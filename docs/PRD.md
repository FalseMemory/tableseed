## 1. 背景

测试数据构造在关系型系统里长期靠手写 SQL 脚本完成，随着表数量与业务规则增长，暴露三个结构性问题：

1. **规则不可复用**：枚举取值、码值描述、边界值分散在几十份 INSERT 脚本中，改一处漏三处；
2. **跨表不可保证**：父子表靠人工对齐，交易表造 100 条、详情表只跟上 87 条，或币种两表不一致；
3. **覆盖不可证明**：跑完造数脚本，没人说得清"4 个状态 × 3 个币种 × 5 个渠道"里到底覆盖了哪些组合，测试结论因此不可信。

现有工具（Faker、FactoryBoy、各类 seed 生成器）解决的是**单表单行**的字段填充，对**多表联动**与**组合覆盖**没有表达能力。

tableseed 的定位是把"造数"从**写脚本**变成**写配置**：用「字段分组」描述单表规则，用「表间关系」描述跨表联动，并让覆盖度成为可计算、可验证的量。

## 2. 目标

### 2.1 产品目标

| 编号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | **覆盖可证明** | `plan` 输出理论组合数；生成后输出实际覆盖与未覆盖组合清单 |
| G2 | **跨表一致** | 生成结果满足全部声明的 `invariants`，外键完整性 100% 通过 |
| G3 | **可复现** | 同配置 + 同 seed，两次生成结果完全一致（可做黄金文件对比） |
| G4 | **规则集中** | 单表的全部造数规则收敛到一份 YAML，可 diff、可评审、可版本化 |

### 2.2 非目标（本期明确不做）

- **不做数据脱敏**：从生产数据脱敏不在范围内，这是另一类工具；
- **不做生产数据回放/流量录制**；
- **不做非关系型存储**（MongoDB / Elasticsearch）；
- **不做性能压测数据生成**（面向功能测试与数据核对，不面向压测）；
- **不做数据可视化报表系统**（WebUI 只交付造数验证所需的最小视图，不做 BI 看板）；
- **不做多人协作与权限体系**（WebUI 定位为单机/内网自用工具）。

## 3. 目标用户与场景

**用户角色**：测试工程师（主要）、开发工程师、数据核对人员。

| 场景 | 描述 | 依赖能力 |
| --- | --- | --- |
| **S1 单表全组合覆盖** | 账户表需覆盖「状态 × 币种 × 渠道」全部组合，验证每个组合下的业务分支 | 分组 + 笛卡尔积 + 覆盖报告 |
| **S2 主子表联动** | 交易表与交易详情表 1:1，详情表的币种、日期、账号、金额必须与主表一致或满足换算关系 | 表间关系 + 字段传播 + 1:1 分配 |
| **S3 对账数据构造** | 造出一批流水与余额，且余额严格由流水汇总得出，用于验证对账逻辑 | `aggregate` 回填 + `invariants` |
| **S4 边界与异常值** | 造出金额上限、超长字符串、空值、负数等边界样本 | `boundary` 组 |
| **S5 组合规模可控** | 组合数上千时，用最少的行数覆盖所有字段对 | `pairwise` 策略 |
| **S6 浏览器内验证** | 不想对着终端，在页面里改配置、跑预演、看结果、导数据 | WebUI（FR-11） |
| **S7 马上看插入的数据** | 入库后想立刻确认数据长什么样，不想切到数据库客户端 | SQL 查询台（FR-12） |
| **S8 快速分享配置** | 把一套造数规则发给同事，对方拿到即可运行 | 单文件 YAML |

## 4. 术语

| 术语 | 含义 |
| --- | --- |
| 组（Group） | 单表内字段的划分单元，是造数的最小规则单元；一个组含一个或多个字段 |
| 有限取值组 | 有确定取值集合的组（enum / boundary / dict），参与笛卡尔积 |
| 每行附着组 | 无固定取值集的组（sequence / random / const / derive / ref），逐行现算 |
| 跨表汇总组 | `aggregate`，依赖子表结果，在 Phase 2 回填 |
| 分配策略 | 1:1 关系下，在固定行数内分配有限取值的方式（follow_parent 等） |
| 锚点 | 父子表配对的关联字段对（join key） |
| 不变量 | 生成后必须成立的断言，用于验证跨表口径 |

> 模型的完整定义见 [README.md](../README.md) 第一章与第二章。

| 编号 | 需求 | 优先级 | 里程碑 |
| --- | --- | :---: | :---: |
| FR-3.1 | 有限取值组之间按**笛卡尔积**展开，每个组合生成一行 | P0 | M1 |
| FR-3.2 | 每行附着组逐行生成，不改变行数 | P0 | M1 |
| FR-3.3 | `plan` 预演：不产出数据，打印各表组合数、行数、依赖序 | P0 | M1 |
| FR-3.4 | 展开顺序稳定（同一配置每次展开顺序一致） | P0 | M1 |

### FR-4 统一表达式

| 编号 | 需求 | 优先级 | 里程碑 |
| --- | --- | :---: | :---: |
| FR-4.1 | `when` / `exclude` / `derive.expr` / `aggregate.expr` / `invariants` 复用**同一套表达式语法** | P0 | M1（M1 仅需 derive） |
| FR-4.2 | 表达式可访问变量：本表字段名、`row`（当前行）、`seq`（行序号）、`seed` | P0 | M1 |
| FR-4.3 | 表达式中可访问 `parent.*`（父行字段）、`src.*`（传播源字段） | P1 | M2 |
| FR-4.4 | 提供函数库：数值、字符串、日期、字典取值、随机（受 seed 控制） | P0 | M1 |
| FR-4.5 | 表达式沙箱：禁止 import、属性访问、任意函数调用（见 NFR-3） | P0 | M1 |

### FR-5 规模治理

| 编号 | 需求 | 优先级 | 里程碑 |
| --- | --- | :---: | :---: |
| FR-5.1 | `max_rows` 硬上限，超出报错（非静默截断） | P1 | M3 |
| FR-5.2 | `exclude` 声明非法组合并剔除，剔除后重新校验覆盖 | P1 | M3 |
| FR-5.3 | `strategy: full` 全组合（默认） | P0 | M1 |
| FR-5.4 | `strategy: pairwise` 两两组合覆盖 | P1 | M3 |
| FR-5.5 | `strategy: sample(n)` 抽样并输出未覆盖清单 | P1 | M3 |

### FR-6 表间关系

| 编号 | 需求 | 优先级 | 里程碑 | 状态 |
| --- | --- | :---: | :---: | :---: |
| FR-6.1 | 关系四要素声明：`cardinality` / `existence` / `join` / `propagate` | P1 | M2 | ✅ |
| FR-6.2 | 基数支持 1:1 / 1:0..1 / 1:N / N:M | P1 | M2 | ✅ 除 N:M（M4） |
| FR-6.3 | 存在性支持 required / optional / conditional | P1 | M2 | ✅ |
| FR-6.4 | 锚点支持主键传播、业务键关联、复合键 | P1 | M2 | ✅ join 自动补齐 copy |
| FR-6.5 | 传播模式：`copy` / `derive` / `map` / `free` | P1 | M2 | ✅（`split` M4 / `aggregate` M3） |
| FR-6.6 | 1:1 关系下有限取值组改用分配策略（follow_parent 默认 / round_robin / random / weighted） | P1 | M2 | ✅ |
| FR-6.7 | 1:1 关系下行数必须等于父行数（关键约束，需专门断言） | P1 | M2 | ✅ |
| FR-6.8 | `ref` 组只能从父表已生成的行中取值，保证引用完整性 | P1 | M2 | ✅ |

**M2 补充决策**：

- **D-7（新增）`follow_parent` 的确切语义** —— 按驱动字段（``drive_by``）分组：
  驱动值首次出现时从组合池轮转取下一个（保覆盖），再次出现时复用上次组合（保一致）。
  未显式声明 `drive_by` 时按「被 copy/map 的父字段 → join 父字段」推断。
- **D-8（新增）被传播覆盖的字段无需归组** —— 完备划分要求的是「每个字段有且仅有一个取值来源」，
  `propagate` 本身即来源之一，故 `check` 对这类字段豁免「未分组」报错。

### FR-7 两阶段生成

| 编号 | 需求 | 优先级 | 里程碑 |
| --- | --- | :---: | :---: |
| FR-7.1 | 依赖图构建：正向 FK 边 + 反向 aggregate 边 | P1 | M3 |
| FR-7.2 | 拓扑排序确定表生成次序；除 aggregate 回边外存在环即报错 | P1 | M3 |
| FR-7.3 | Phase 1 正向生成（父 → 子） | P1 | M3 |
| FR-7.4 | Phase 2 反向回填（子 → 父），按锚点聚合 | P1 | M3 |
| FR-7.5 | `aggregate` 表达式支持：count / sum / avg / min / max / count_distinct，`by <锚点>` 分组 | P1 | M3 |

### FR-8 执行与输出

| 编号 | 需求 | 优先级 | 里程碑 |
| --- | --- | :---: | :---: |
| FR-8.1 | **提供数据库连接时：直接执行入库**（分批提交）；支持 `--dry-run` 只看不写 | P0 | M1 |
| FR-8.2 | **未提供数据库连接时：只生成不落盘**，返回内存对象，不产生任何文件副作用 | P0 | M1 |
| FR-8.3 | 内存对象提供多种导出形态：`to_dataframe()` / `to_records()` / `to_sql()` / `to_csv()` | P0 | M1 |

## 6. 非功能需求

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |

| NFR-3 | **安全**：表达式为受限沙箱，禁止任意代码执行；工具只读元数据，绝不修改目标库结构 | 安全测试用例（注入表达式应被拒绝） |
| NFR-4 | **可移植**：Windows / Linux 均可运行 | 双平台 CI 或人工验证 |
| NFR-5 | **可测试**：核心逻辑（展开、分配、拓扑、表达式）与 IO 解耦，可纯内存单测 | 覆盖率 ≥ 80% |
| NFR-6 | **报错可读**：配置错误需指出文件、行号、字段路径与修复建议 | 人工评审 |
| NFR-7 | **本地安全**：WebUI 默认仅监听 `127.0.0.1`；SQL 控制台默认只读白名单 | 安全测试 |
| NFR-8 | **无副作用**：未提供数据库连接时，生成过程不写磁盘、不建临时文件 | 断言工作目录无新增文件 |

## 7. 验收标准（M1 端到端）

以 README 中的示例配置为基准，M1 完成的定义是下列断言全部成立：

| 编号 | 断言 |
| --- | --- |
| AC-1 | `tableseed check -c sample.yaml` 退出码 0，无错误 |
| AC-2 | `tableseed plan` 输出 `t_account` 组合数为 `2 × 2 × 3 = 12` |
| AC-3 | `tableseed gen` 产出的 `t_account` 恰好 12 行 |
| AC-4 | 12 行的状态/币种/渠道组合互不相同，且等于理论组合集合（无重复、无遗漏） |
| AC-5 | 每行的 `status_desc` 与 `status_code` 严格配对 |
| AC-6 | `acct_no` 按自增组规则连续，`tenant_id` 全行相同，`balance` 在声明区间内 |
| AC-7 | 连续两次生成（同 seed）输出文件字节级一致 |
| AC-8 | 故意将某字段从所有组中移除后运行 `check`，报错并指名该字段 |
| AC-9 | 生成的 SQL 可在目标库直接执行成功 |
| AC-10 | `tableseed ui` 启动后浏览器可用，加载示例配置并实时校验通过 |
| AC-11 | 页面点击生成后，结果表格显示的 12 行与 CLI 输出完全一致 |
| AC-12 | SQL 控制台执行 `SELECT` 返回结果并渲染表格；执行 `DELETE` / `DROP` 被拒绝并给出原因 |
| AC-13 | 未提供数据库连接时执行生成，工作目录内无任何新增文件（NFR-8） |

### 7.2 M2 端到端（samples/txn.yaml）

| 编号 | 断言 |
| --- | --- |
| AC-14 | `t_txn` 9 行、`t_txn_detail` 9 行、`t_txn_log` 27 行（基数 1:1 / 1:N 生效） |
| AC-15 | 每条子行的 `txn_no` 在父表中存在（join 自动 copy） |
| AC-16 | `copy` 传播：子行 `currency` 与父行一致 |
| AC-17 | `map` 传播：`T/D/W` 映射为 `TRANSFER/DEPOSIT/WITHDRAW` |
| AC-18 | `derive` 传播：子行 `net_amount == parent.amount - parent.fee` |
| AC-19 | `follow_parent` 一致性：同一 `txn_type` 的行，子表 `settle_status` 相同 |
| AC-20 | `follow_parent` 覆盖性：3 个 `settle_status` 全部出现 |
| AC-21 | 1:N 下每条父行都拥有完整的 3 个子表组合 |
| AC-22 | `plan` 输出生成顺序 `t_txn → t_txn_detail → t_txn_log`，行数与实造一致 |
| AC-23 | 关系成环时 `check` 报错并指出可疑环 |
| AC-24 | `ref` 组取值来自父行；引用不存在字段时报错并列出可用字段 |

## 8. 里程碑

## 9. 风险与开放问题

| 编号 | 风险 / 问题 | 影响 | 应对 |
| --- | --- | --- | --- |
| R-1 | 表达式语法最终形态未定（`==` vs `=`、聚合 `by` 语法） | 影响 FR-4 全部需求 | M1 前冻结语法并在本文档附录标注 |
| R-2 | pairwise 算法实现成本（IPOG 完整版较复杂） | 可能拖慢 M3 | 先用贪心近似实现，覆盖度达到 100% 对覆盖即可 |
| R-3 | 方言差异（Oracle 序列、隐式类型转换、标识符大小写） | 影响 FR-1.4 / FR-8.1 | 方言层做隔离，M1 先支持 PostgreSQL + MySQL，Oracle M2 补 |
| R-4 | 组合爆炸的默认阈值定多少合适 | 影响易用性 | 暂定 `max_rows` 默认 10 万，超出必须显式调高 |
| R-5 | 复杂业务规则（如状态机、跨字段约束求解）表达能力不足 | 可能无法覆盖部分场景 | 本期不引入状态机，用 `when` + `exclude` 组合逼近，列入后续版本评估 |
| R-6 | 与现有测试平台的集成方式未定 | 影响落地路径 | M2 后评估 CLI 调用 / Python API 两种集成形态 |

## 10. 决策记录

### 已确认（2026-09-10 评审）

| 编号 | 问题 | 结论 |
| --- | --- | --- |
| D-1 | 是否同步做 GUI | **是**。验证阶段以浏览器为主要交互面，GUI 由 M5 提前至 M1 起同步交付 |
| D-2 | 是否提供 SQL 执行入口 | **是**。WebUI 内置 SQL 查询台，默认只读白名单（FR-12） |
| D-3 | 表达式语法风格 | **参考 Python + MySQL**：逻辑与比较运算符沿用 Python（`and` / `or` / `not`、`==`），同时接受 MySQL 风格（`AND` / `OR` / `NOT`、`<>`、`LIKE`、`IS NULL` / `IS NOT NULL`、`BETWEEN ... AND ...`）；函数库提供 Python 与 MySQL 双风格别名（见 tech-design 第 6 节） |
| D-4 | 配置是否拆分多文件 | **不拆分**。保持单文件 YAML，便于直接分享与传递；超大配置用 YAML anchor / alias 复用 |
| D-5 | 输出目标形态 | **按连接有无分派**：提供数据库连接则直接执行入库；无连接则只生成不落盘、返回内存对象（DataFrame / records），默认无磁盘副作用（FR-8） |
| D-6 | 子命令命名 | `plan` / `check` / `gen` / `verify` / `ui` 五个 |
